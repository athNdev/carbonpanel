Carbon Panel can expose a read-first [Model Context Protocol](https://modelcontextprotocol.io/)
(MCP) stdio server to an AI assistant. The MCP artifact is independently
versioned and owned: it does not move a panel release tag, a Docker Hub panel
image or a GitHub Release. See [ADR 0034](https://github.com/athNdev/carbonpanel/blob/main/docs/adr/0034-mcp-server-distribution.md).

The gateway mounts the generated **211-tool combined catalogue**. It is derived
from 250 declared RPCs across 28 proto services, of which 240 are mounted/reachable
across 27 mounted services. Tool coverage is not the same as RPC coverage;
the audit matrix records 200 supported operations (all listed, reachable and
verified) and 78 excluded operations with exact reasons and equivalent flows.

## Two different claims: available versus compatible

- **Public package availability** means the official OCI artifact and registry
  listing exist, are immutable and install. It says nothing about your panel.
- **Compatible server capabilities** means the panel build behind
  `CARBONPANEL_URL` actually implements the RPC backing a tool. It is
  determined from a tested, pinned panel build.

A successful `docker pull`, client handshake or `tools/list` is **not** proof
that a tool works. Never infer capability from the MCP client version.

## Choose the panel build first

The default is your **existing stable install**. The latest stable panel is
`v1.0.40` (`f88748be6a216b187e675bbb1f110df07e544148`). The pinned post-stable
build (`fa23a8d73c181f9907633024d9023aead928324e`) adds the new RPCs, but it is
not the stable install path. The panel must have authentication enabled: legacy
no-auth installations are refused.

- **New self-hosted install:** you MAY start one by following [Docker Compose](../getting-started/docker-compose/)
  or [prebuilt binaries](../getting-started/prebuilt-binaries/), open
  [http://localhost:8080](http://localhost:8080), create the first administrator account, then create
  a dedicated API token. A new install must NOT replace, reconfigure, migrate
  or delete an existing panel, world or database; if one already exists, use
  it instead. Install the panel before attaching MCP.
- **Existing self-hosted install:** do not re-run an installer over it. Keep
  the existing `config.yaml`, controller database, worlds and backups. Only
  create a scoped token with an expiry and point the client at the existing
  panel URL.

Switching an existing install to nightly is **never automatic**. It is only an
operator-initiated change: back up the database and worlds, choose a qualified
build explicitly and verify it before pointing MCP at it. Connecting or
smoke-testing the MCP server must never restart shared services or rewrite
data.

## Pin the official artifact

Pin one exact stable MCP artifact version and its immutable `sha256` digest.
Never use `latest`, `@main`, a branch tag, a moving minor tag or a locally
built image. The Go SDK and artifact versions are independent of the panel
release version; the local manifest is [`docker/mcp.server.json`](https://github.com/athNdev/carbonpanel/blob/main/docker/mcp.server.json)
and it currently carries an all-zero placeholder digest until a real digest is
published. `scripts/validate_mcp_server_json.py` checks the required fields and
refuses `latest`; the publication workflow injects the verified digest before
any registry write.

## Authentication is required

The MCP server refuses a legacy no-auth installation. It verifies that
authentication is enabled (`AuthService/GetAuthStatus`) and uses the token's
identity for authorization. A missing or invalid credential is an error; there
is no anonymous fallback and no way to connect to a panel with authentication
disabled.

## Create a dedicated token

In the panel, create an API token with the narrowest permissions and a finite
expiry. It must be a real `dp_` token, not a browser session token or an
anonymous bypass. Pass it only through `CARBONPANEL_TOKEN` in the client
configuration (or an environment variable). Do not put a token in command
arguments, commit it to a repository or write it to stdout. The registry
metadata marks this variable `isSecret: true`.

## Client configuration

The URL must be reachable **from where the MCP process runs**. Pick one case.

**(a) Host-installed MCP binary** — loopback on the host reaches a panel
published on that host:

```json
{
  "mcpServers": {
    "carbon-panel": {
      "command": "<PATH_TO_MCP_BINARY>",
      "args": ["stdio"],
      "env": {
        "CARBONPANEL_URL": "http://127.0.0.1:8080",
        "CARBONPANEL_TOKEN": "dp_<DEDICATED_EXPIRING_API_TOKEN>"
      }
    }
  }
}
```

Use the official stable binary release and verify its published checksum; never
a locally built or preview binary.

**(b) Compose-deployed MCP container** — the MCP process is in a separate
container, so it must use the panel's Compose service DNS name and port:

```json
{
  "mcpServers": {
    "carbon-panel": {
      "command": "docker",
      "args": [
        "run", "-i", "--rm",
        "--network", "<COMPOSE_NETWORK>",
        "-e", "CARBONPANEL_URL",
        "-e", "CARBONPANEL_TOKEN",
        "ghcr.io/athndev/carbonpanel-mcp:<STABLE_VERSION>@sha256:<64_HEX_DIGEST>"
      ],
      "env": {
        "CARBONPANEL_URL": "http://carbon-panel:8080",
        "CARBONPANEL_TOKEN": "dp_<DEDICATED_EXPIRING_API_TOKEN>"
      }
    }
  }
}
```

Get `<COMPOSE_NETWORK>` from `docker compose config`; the service name is
`carbon-panel` in the shipped Compose file. Never use `localhost` or
`127.0.0.1` as a fallback inside the MCP container: that address is the MCP
container itself. The shipped Compose file uses host networking by default,
which suits case (a); a separate container still needs a shared network and
DNS. No world, database, backup or Docker socket mount is used in either case.
The process is non-root, serves JSON-RPC on stdin/stdout, writes diagnostics
to stderr and exits on stdin EOF. There is no HTTP healthcheck port: the stdio
session is the liveness signal.

### OS-specific notes

- **Windows:** use Docker Desktop with WSL2 and
  `%APPDATA%\Claude\claude_desktop_config.json`. Double backslashes in any
  host path you add. Only Linux is fully supported and tested; Windows
  installations may have issues.
- **macOS:** use `~/Library/Application Support/Claude/claude_desktop_config.json`.
  The multi-arch image provides `arm64` for Apple Silicon and `amd64` for
  Intel; pull by manifest digest so the client resolves its own platform.
- **Linux:** use `~/.config/Claude/claude_desktop_config.json` and keep it
  readable only by your user (`chmod 600`).

## Compatibility matrix

Tool names match the implemented **combined 211-tool catalogue** exactly
(250 declared RPCs, 240 mounted/reachable). All ten tools below are mounted; the
columns report whether the panel build behind `CARBONPANEL_URL` implements the
RPC that backs each tool. Exclusions and policy boundaries are recorded in the
OSS-375 audit matrix.
Evidence basis: the RPC list at tag `v1.0.40` (`f88748be…`) and at the
pinned post-stable build `fa23a8d73c181f9907633024d9023aead928324e`, read from
the checked-in protos. "Qualification pending" means the RPC exists in that
build but no passing smoke evidence has been recorded for it yet.

| MCP tool | Backing RPC | `v1.0.40` | Pinned post-stable build |
| --- | --- | --- | --- |
| `list_servers` | `ServerService/ListServers` | available | available |
| `get_server` | `ServerService/GetServer` | available | available |
| `list_files` | `FileService/ListFiles` | available | available |
| `get_file` | `FileService/GetFile` | available | available |
| `list_backups` | `BackupService/ListBackups` | available | available |
| `list_players` | `PlayerService/ListPlayers` | RPC absent (tool mounted) | mounted; pinned, qualification pending |
| `get_player` | `PlayerService/GetPlayer` | RPC absent (tool mounted) | mounted; pinned, qualification pending |
| `list_world_entries` | `WorldService/ListWorldEntries` | RPC absent (tool mounted) | mounted; pinned, qualification pending |
| `list_world_view_targets` | `WorldViewService/ListWorldViewTargets` | RPC absent (tool mounted) | mounted; pinned, qualification pending |
| `get_world_view_status` | `WorldViewService/GetWorldViewStatus` | RPC absent (tool mounted) | mounted; pinned, qualification pending |

A tool is qualified only after its RPC is present in an explicitly pinned build
and a smoke result for that build is retained. Until then it must be reported as
not qualified on that build rather than attempted optimistically.

## Verified minimal smoke on stable

The verified minimal tool set that works against `v1.0.40` is `list_servers`,
`get_server`, `list_files`, `get_file` and `list_backups`, matching the core
lane's stable smoke path. This is a **verified-by-contract** set: the RPCs were
read directly from the tagged protos. Execution against a real `v1.0.40`
fixture is a separate gate and has not been performed in this change.

1. Check the panel health endpoints before connecting: `GET /healthz`,
   `GET /readyz` and `GET /health/detail`. Report `healthy`,
   `degraded`/`unavailable` and `unknown` separately. A stored `Running` status
   is not playable evidence, and a missing check is never reported healthy.
2. Start the pinned image by digest with a dedicated token and call
   `tools/list`. The stable tool set above may be listed; listing a main-only
   tool is not proof that it works.
3. Call `list_servers` and show the unmodified result. Optionally call
   `get_server` with a server id, then `list_files`/`get_file` (bounded,
   server-relative) and `list_backups`.
4. No write, restart, delete, prune or config/world/database change is
   attempted, so no rollback is needed.
5. If a tool returns `Unimplemented` or an unavailable-RPC error, stop that
   call and surface the structured capability error below. Do not retry with a
   different MCP client version and do not report the call as successful.
6. Confirm stdout contains only JSON-RPC and diagnostics go to stderr, then
   remove the owned fixture. See [MCP distribution smoke](https://github.com/athNdev/carbonpanel/blob/main/docs/runbook-mcp-smoke.md)
   for the full evidence and hard-stop procedure.

## Capability errors

When a tool's RPC is absent, `Unimplemented` or unavailable, return an MCP
tool error (`isError: true`) with an honest structured payload:

```json
{"error":{"code":"CAPABILITY_UNAVAILABLE","tool":"list_players",
 "rpc":"carbonpanel.v1.PlayerService/ListPlayers",
 "required_panel_build":"post-v1.0.40+fa23a8d73c181f9907633024d9023aead928324e","observed_panel_build":"v1.0.40 (f88748be)",
 "retryable":false,"guidance":"Upgrade the panel in a separate operator-initiated change."}}
```

The semantic requirement (`CAPABILITY_UNAVAILABLE`, named tool/RPC, required
and observed builds, no false success, no silent omission) is fixed by
[ADR 0034](https://github.com/athNdev/carbonpanel/blob/main/docs/adr/0034-mcp-server-distribution.md).
The exact wire field names are owned by the core implementation lane and must
be kept in sync with this guide.

:::caution[Data preservation]
Do not run `docker compose down -v`, `docker system prune`, `rm -rf` on data
paths, or any delete/stop/start/recreate command as part of connecting or
smoke-testing MCP. Keep world data and the panel database intact before and
after. Stop and report if any tool asks for a write.
:::
