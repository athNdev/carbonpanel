Carbon Panel includes a read-first Model Context Protocol (MCP) stdio gateway.
The gateway's OCI package has its own version and release workflow.
[Distribution decision](https://github.com/athNdev/carbonpanel/blob/main/docs/adr/0034-mcp-server-distribution.md)

The gateway mounts the generated **211-tool combined catalogue**. It is derived
from 250 declared RPCs across 26 proto services, of which 240 are mounted/reachable
across 27 mounted services. Tool coverage is not the same as RPC coverage;
the audit matrix records 201 supported operations (all listed, reachable and
verified) and 77 excluded operations with exact reasons and equivalent flows.

## Choose the panel build first

Connect to your existing authentication-enabled panel and record its version
and commit for the compatibility check. For a new panel, install a separate
Stable instance and create the first administrator account before connecting
MCP. Preserve any existing panel, worlds and database.
[Docker Compose](../../getting-started/docker-compose/) · [Prebuilt binaries](../../getting-started/prebuilt-binaries/)

Choose any panel upgrade or channel change separately and follow the panel
upgrade procedure with backups.

## Pin the official artifact

Look up the exact registry name and version, copy the OCI package identifier
with its `sha256` digest, and confirm you can pull that digest anonymously.
The manifest in the source tree carries a placeholder digest for the
publication workflow. [Official MCP Registry](https://registry.modelcontextprotocol.io/v0.1/servers?search=io.github.athNdev%2Fcarbon-panel)

## Create a dedicated API token

The gateway verifies that panel authentication is enabled and checks the API
token's identity at startup. Create a dedicated account with `servers:read` on
the servers you want to list. Grant `files:read` for file calls and
`backups:read` for backup calls on those servers as needed. An API token
inherits its owner's grants, so mint an expiring `dp_` token from that
account.

Supply the token through the client's secret store or private environment
configuration as `CARBONPANEL_TOKEN`. Keep the value out of shell arguments,
logs and source control.

## Client configuration

Use a Docker runtime that can launch Linux containers from your MCP client.

- **Windows** uses Docker Desktop with the WSL 2 backend and Linux containers.
- **macOS** uses Docker Desktop. The digest selects a Linux image for Apple
  Silicon or Intel.
- **Linux** uses Docker Engine. Run `docker` from the same account as the MCP
  client and restrict access to any client configuration containing a token.

Use a controller URL reachable from the MCP container. This example starts
the official image on a shared Compose bridge network. Replace the network,
image and token placeholders with your own values.

```json
{
  "mcpServers": {
    "carbon-panel": {
      "command": "docker",
      "args": [
        "run", "-i", "--rm",
        "--network", "<COMPOSE_NETWORK>",
        "-e", "CARBONPANEL_URL",
        "-e", "CARBONPANEL_TOKEN",
        "ghcr.io/athndev/carbonpanel-mcp:<STABLE_VERSION>@sha256:<64_HEX_DIGEST>"
      ],
      "env": {
        "CARBONPANEL_URL": "http://carbon-panel:8080",
        "CARBONPANEL_TOKEN": "dp_<DEDICATED_EXPIRING_API_TOKEN>"
      }
    }
  }
}
```

Use `docker compose config` to identify the service and bridge network for
your installation. The shipped Compose example uses host networking by
default. For a host-networked or remote panel with an existing HTTPS address,
use that address if reachable from the container and omit the shared network
argument. Container loopback reaches only the MCP process's own container.

The gateway runs as a non-root stdio process with JSON-RPC on stdout,
diagnostics on stderr and a clean exit on stdin EOF. It needs no panel data
mounts or Docker socket mount.

### Development with a locally built binary

For repository development, build `./cmd/carbonpanel-mcp` from the checkout.
The binary starts stdio with no arguments. When it runs on the same host as a
panel listening on port 8080, use the host's loopback address.

```json
{
  "mcpServers": {
    "carbon-panel": {
      "command": "<PATH_TO_MCP_BINARY>",
      "args": [],
      "env": {
        "CARBONPANEL_URL": "http://127.0.0.1:8080",
        "CARBONPANEL_TOKEN": "dp_<DEDICATED_EXPIRING_API_TOKEN>"
      }
    }
  }
}
```

## Check the connection

1. From the MCP container's network, check `GET /healthz`, `GET /readyz`
   and `GET /health/detail`. Report each observed status. A stored
   `Running` state alone cannot verify that a player can join.
2. Start the pinned gateway and call `tools/list`, then `list_servers`.
   Record the result with the installed controller build.
3. If you have read access to a known server, optionally call `get_server`,
   `list_files`, `get_file` with a server-relative path, or `list_backups`.
   Keep the check read-only.

## Capability errors

When the controller reports a missing procedure, the gateway returns
`isError: true`. The `structuredContent` identifies the affected tool and
the catalog's minimum panel build.

```json
{
  "status": "error",
  "error": {
    "kind": "capability_unavailable",
    "code": "unimplemented",
    "message": "The controller reported an unimplemented procedure.",
    "tool": "list_players",
    "procedure": "/carbonpanel.v1.PlayerService/ListPlayers",
    "minimum_panel_build": "post-v1.0.40+fa23a8d73c181f9907633024d9023aead928324e"
  }
}
```

Record the installed controller build separately. A missing domain record uses
`error.kind: not_found`, and an authorization denial uses
`error.kind: permission_denied`.
