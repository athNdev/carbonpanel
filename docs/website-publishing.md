# Website and pinned documentation

The Pages deployment contains the homepage at `/`, documentation at `/docs/`
and the shared design system at `/design-system/`. Explicit site-only deploys,
automatic docs-only deploys, channel promotions and recovery all use the
non-cancelling `pages-deploy` queue. Each publisher qualifies the live source
under the shared lock before replacing the canonical site.

## Source contract

`docs/website-source.json` is the SINGLE machine-readable build contract.
Schema 3 publishes exactly two channels: `Stable` (`v1.0.40`, version `1.0.40`,
verified commit `f88748be…`) at `/docs/`, and `Nightly` (the qualified rolling
revision) at `/docs/nightly/`. Each channel records its full commit, image refs
for BOTH Docker Hub and GHCR, one shared digest and the same exact revision.
The current Docker Hub baseline `d8597d4e…` / `sha256:ecc89ba9…` is accepted
only as a recorded bootstrap pending GHCR qualification; otherwise promotion
uses the first qualified current-main pair. `scripts/version_contract.py`
derives the shared `docs/version-index.json` from this contract, re-verifies the
stable entry against the classified catalog `docs/release-history.json`, and
fails closed on extra channels, missing markers, stale revisions or retired
snapshots. The catalog and its historical source-tag records stay intact; the
legacy doc snapshots `1.0.39` and `3.0.0-alpha.1` are not published or offered
in the selector.

The public selector vocabulary is exactly `Stable` and `Nightly`, with no
version numbers or legacy snapshot names. The proto's `2.x` declares the independent Connect-OpenAPI schema family;shipped bundled and website schema copies stamp `info.version` with the exact
product version (CLI `--version`, UI runtime `build/version.json` and release
manifest agree), and the same stamped input becomes the schema embedded in the
packaged panel and served by its running OpenAPI handler. The runtime UI version
is read from `build/version.json`, generated by the same `getVersion()` that
defines `__APP_VERSION__`; an incidental version string in an unrelated asset
is not accepted. Protocol `v1` stays unchanged.

The contract is validated fail-closed: the stable commit must match the catalog
peel **and** the real Git tag resolved at build time; each channel's image
revision must equal its commit, and the published index must equal the source
contract. A tag-ID, peel, digest, marker or channel disagreement aborts before
packaging.

The builder exports the authored guides and all imported Compose, configuration,
OIDC and protobuf sources from each exact pinned commit into a temporary
directory. It generates every API schema using Buf 1.50.0 and the pinned
OpenAPI plugin. The current branch supplies only the website presentation
(theme, navigation, components); authored content including the docs home comes
from the pinned commit and the identity page is generated from the contract.
No build reads application examples from a floating branch.

### Maintained operational guides

A narrow class of release-independent operational pages is maintained on the
first-party docs source instead of being frozen to a product release. Today that
is the Proxmox first-party install/update guide and the single Proxmox answer in
the FAQ. `docs/maintained-guides.json` is only a classification/path/compatibility
declaration: which slugs are maintained, the exact source path and page mode
(`page` replaces a whole page; `fragment` replaces one `<details>` answer), and
the guarantees that every slug exists in each pinned channel and that product
pins, markers and generated schema stay untouched. It deliberately contains no
revision and no content hashes; those would recreate the stale pin this model
exists to avoid.

The exact source revision is the checked-out `git HEAD` of the trusted website
build, and nothing else: there is no secondary revision input that could
disclose an older or foreign guide. Guide text is read from those exact
Git blobs, overlaid onto each exported channel snapshot before link rebasing,
and attested with its SHA-256 in a generated `maintained-guides.json` beside the
channel's `source.json`. A whole maintained page also carries a visible
**Guide source** link to the exact authored blob at that revision, so readers do
not mistake the `Pinned to` application link for the guide's source. Editing a
maintained guide in a later commit therefore
refreshes both channels and their attested digests on the next build with no
manifest edit. Channel identity, pinned prose outside the declared files, aliases
and generated schema are never rewritten. An allowlist path, missing or
duplicate entry, absent source blob, absent pinned slug, floating ref or broken
fragment anchor aborts the build. `scripts/test_maintained_guides.py` exercises
the real pinned snapshots for both active channels and the no-manifest-edit
refresh at the integration seam; Website Checks runs it on every docs change.
The decision and its rationale are in
[ADR 0050](adr/0050-maintained-operational-guides.md).

#### Automatic docs-only publication

`.github/workflows/docs-only-publish.yml` republishes changed maintained guides
without a manual dispatch, a registry alias move or a release. It runs on a
**successful CI completion on trusted `main`** (push event, 40-hex head),
checks out and asserts that exact tested commit, re-verifies exact-commit main
CI, and rechecks that `main` still points at that commit immediately before the
Pages write. The trigger is a liveness decision over real bytes: `guide-evidence`
reads the live maintained-guide receipts for both channels and
`guide-change-decision` publishes only when a slug set, bytes, paths, scopes or
declaration hash is **missing or stale**. A later CI commit on main with
identical maintained inputs is a visible no-op; the tested revision qualifies
the build, not the liveness decision.

The boundary between **stale** and **blocked** is explicit in the job outputs
and summary. A stale or missing live guide receipt is a reason to publish and
is recorded with the differing channels and fields. A failed exact-commit CI
check, an unresolved or mismatched live Stable/Nightly product/image receipt, a
main tip that moved after pinning, or an unverified rollback baseline is a
blocked qualification: the job stops with zero Page, alias, tag, release or
tracked-file writes and reports the failing reason. No failed or PR event may
occupy the shared `pages-deploy` queue. Eligible jobs use `queue: max` with
cancellation disabled and verify the current source after acquiring the lock.

Before any deploy the shared `docs_publication_gate` resolves the live
Stable/Nightly receipt, rebuilds the **full** two-channel site from that exact
state plus the tested guide bytes, and proves it preserves the same commit,
digest, selector and rendered canonical pages. Rollback bytes come from the
**last successful GitHub Pages deploy step**. Follow the deployment status
to its exact Actions job, skip jobs whose Pages steps were all skipped, and
select the archived artifact named by the final deploy step. That artifact is
accepted only when its index, receipts, manifests and every declared page are
byte-equal to the live site. An equal `version-index.json` alone is never
enough — a docs-only rebuild can share it while serving different guide bytes.
Only when that artifact is no longer retained may the gate reconstruct a baseline from
the exact deployment SHA confirmed on `origin/main`, in a separate worktree;
live state is re-qualified and all live bytes compared, and the result is
reported as `reconstructed`, never as the original artifact. A missing or
unverified baseline blocks the deployment. Management of these gates lives in
`scripts/docs_publication_gate.py` and
`scripts/test_docs_publication_gate.py`; the channel-promotion lane reuses the
same successful-deployment identity and byte-qualified artifact check.

## Multi-version documentation

The stable default is `/docs/`, with an immutable mirror at
`/docs/versions/1.0.40/`. Nightly is built at `/docs/nightly/`. The legacy
snapshot routes `/docs/versions/1.0.39/` and `/docs/versions/3.0.0-alpha.1/`
are gone and return 404. Every docs page carries the same accessible channel
dropdown, rendered from the one generated index by `VersionBanner.astro`: a
labelled native `<select>` with visible focus and keyboard navigation, offering
only `Stable` and `Nightly`. It carries the current page when the target channel
has that slug, and otherwise lands on that channel's home; all hrefs are
canonical, with no double slashes or appended version prefixes. The `Pinned to
<short>` link uses `${repository}/commit/<FULL_SHA>` on every route. The same
index drives direct URL validation, search scoping, sitemap/canonical URLs and
Pages metadata. Each channel is a separate Starlight build with its own base,
so asset URLs, search indices and canonical URLs stay isolated. A missing page
falls back to the 404 page under that channel's base.

The same index is published byte-identically at two public URLs: the site root
`/version-index.json` and the documented documentation URL
`/docs/version-index.json`. One SHA-256 therefore verifies either surface.
`check_website.py` fails closed when the `/docs/` copy is missing or drifts
from the root copy, so a dispatch that would leave the documented URL at 404
cannot be called a verified publication.

Older snapshots may use HTML license comments and sidebar slugs that the
current MDX/Starlight tooling no longer accepts. The builder applies a narrow
presentation-only compatibility rewrite: SPDX HTML comments become MDX comments,
the sidebar is generated from the slugs that actually exist at that commit, and
the design-system link depth follows the version route. Authored prose, examples
and pinned public assets still come from the exact peeled commit.

## Promotion marker

The ordinary main build is deterministic and **never claims a promoted nightly**:
the tracked contract keeps the verified Docker Hub baseline with
`promotion.promoted = false`. A promotion gate passes the exact qualified nightly
revision, the single digest verified in both registries, a state (`candidate` or
`final`) and a receipt id as external build input (`--nightly-revision`,
`--nightly-digest`, `--promotion-state`, `--promotion-receipt`, or the equivalent
`CARBONPANEL_PROMOTED_*` environment variables). Nothing writes those values back
to `docs/website-source.json` or `docs/version-index.json`; only the generated
site carries them.

Every build writes `channel-marker.json` at the site root and a
`data-channel-*` marker on each version banner. A `candidate` build is emitted
**only** at the non-active staging route `/docs/candidate/<sha>/` (with its own
marker and index); it never publishes `/docs/`, `/docs/nightly/` or
`/docs/versions/1.0.40/`, which stay on the active verified receipt until the
transaction commits. A candidate is qualified over public HTTPS at that staging
path before any registry alias moves, then the final deployment is checked at
the canonical paths again. `check_website.py --expect-nightly-revision
--expect-nightly-digest --expect-promotion-state --expect-promotion-receipt`
(and `browser_version_check.py` with the `CARBONPANEL_EXPECT_*` variables) fails
closed when the published marker, source pin, pinned `/commit/<FULL_SHA>` links
or digest disagree. Nightly aliases are never derived from a self-tracked build
SHA.

A source pin does not make old prose correct. Authors must review guidance against
the pinned implementation, especially deployment commands, external integrations,
sleep modes, permissions, destructive actions and recovery. Open gaps are tracked
in the [documentation backlog plan](plans/website-documentation-backlog.md).

## Build and verify

Requirements: Git with the pinned commit available, Python 3.12+, Node.js 24.22.1,
Bun 1.4.2, npm and Buf 1.50.0. Network access is needed for locked packages and the
versioned Buf generator. No application, Docker daemon or database is required.

```sh
python3 -m unittest scripts.test_website scripts.test_version_contract scripts.test_maintained_guides scripts.test_landing_page scripts.test_design_system_page
python3 scripts/check_brand_assets.py
python3 scripts/version_bump.py prepare --check
python3 scripts/build_website.py
python3 scripts/check_website.py
python3 scripts/version_bump.py prepare --check --site .website-build/site
cd scripts/manual-review/e2e && bun install --frozen-lockfile && bunx playwright install chromium && cd ../../..
python3 scripts/changelog_browser_check.py
```

`scripts/changelog_browser_check.py` drives the exact built site with the
repository-pinned Playwright helper (`scripts/manual-review/e2e/changelog-switcher-dom.mjs`).
It fails if a changelog route has other than one H1, omits the actual
release/version banner label or canonical release-note link, shows a retired
heading, or if the deep-path channel switcher cannot be clicked from the Stable
archive and Nightly routes at both desktop and mobile widths. This is the same
gate run in `.github/workflows/docs.yml`; no network, registry or deploy write
is performed by the checker.

`scripts/version_bump.py prepare` regenerates the shared index; `prepare
--check` fails on a stale index. `bump <tag> --check` derives a candidate from
the catalog and Git without writing anything; `bump <tag> --apply` updates only
the contract and index. Neither command creates a tag, publishes a release,
writes a registry or marks a candidate published. The check runs on the same
commit for all surfaces, so an omitted surface fails the build. staging and
Pages/GitHub writes are separate, deterministic steps: verify the exact-commit
artifacts first, then redeploy Pages, then verify the published `source.json`,
then reconcile registries/GitHub. There is no cross-provider atomic transaction;
a failed step is retried from the verified artifact, never by moving a published
tag or overwriting a release. See [release operations](releases.md).

Pages publication is an explicit `workflow_dispatch` of
`.github/workflows/landing.yml` with `deploy=true` on the trusted
`refs/heads/main` ref. The dispatched commit is the exact main HEAD at trigger
time; `verify-main-ci` refuses it unless that SHA is an ancestor of `main` and
has a completed successful push run of `ci.yml`. The artifact is the
`github-pages` artifact uploaded by that same run. Derive the documented
publication from the contract (stable tag and peeled commit), not from a
free-form input: after the deploy job succeeds, check the run ID and artifact
SHA-256, then fetch the live `/docs/source.json` (stable tag, channel and
peeled commit), `/docs/version-index.json`, `/docs/` (stable default plus
switcher) and each `/docs/versions/<version>/` route. A missing route is a
failed publication, not a cache delay to be assumed away; retry the dispatch
only after re-verifying the exact-commit artifact, and never retag, overwrite
an immutable route or mutate a registry to reconcile a Pages failure.

Generated output stays in ignored `.website-build/site/`. The builder excludes
landing QA pages. The link check validates local page and asset paths, including
the API iframe, schema and design-system assets, under the deployment base.
The design-system page and tokens come from the current branch, independently
of the application documentation pin. Its source remains usable from a checkout.
Its website header, breadcrumb, local fonts and return links connect it to the
homepage and docs. The builder rebases checkout-relative asset and navigation
links for publication, including installations under a subpath. The homepage
introduces it in the design section; docs also link to it in the sidebar.
The builder writes `sitemap.xml` at the artifact root on every deployment,
including every published HTML route except the synthetic 404 page and a
deployment-date `lastmod` value. Pages with a `noindex` robots directive are
utility pages, are excluded from the sitemap, and may not compete with canonical
documentation. `check_website.py` rejects missing, malformed or incomplete sitemap
output.

For a local preview rooted at the server's root:

```sh
python3 scripts/build_website.py --base /
python3 scripts/check_website.py --base /
python3 -m http.server 18765 --directory .website-build/site
```

Open `http://localhost:18765/` and `http://localhost:18765/docs/`.
Use the default base when preparing a Pages artifact. Test search in a built
preview; Starlight's production search index is generated at build time.

The docs project's normal development server previews working-tree content and
labels its banner accordingly. Use the combined build to verify the publication
pin and generated API schema.

## Interactive homepage fragments

The homepage build compiles three focused Svelte islands from
`web/carbon-panel/demo/`. Their feature components are also consumed by the
installed panel: server lifecycle actions, the Studio mod table, and the update
batch. Each island has independent sample state and a reset. It cannot import
application API clients, stores, SvelteKit routes or Monaco; the Vite build
enforces this boundary. Browser actions simulate changes in memory and never
connect to a server or mod provider.
The Studio island uses Carbon tabs, search, tiles and buttons around its shared
mod table. Its sample catalog demonstrates adding a required dependency and
curating a pack. Twelve catalog entries and six seeded mods support filtering,
paging, bulk side/pin/removal actions and sample updates that respect pins.
Three inspectable override files accompany the export workflow. Building an
export reflects its format, sides, versions and override choices in an inspector
and a downloadable JSON sample manifest (`playable: false`). It includes no mod
binaries, provider IDs or download URLs and is not a playable launcher archive.
Pack or option changes invalidate the previous export preview.

The staging island collects sample edits from six supported staging areas into
the shared update-batch inventory. It shows before/after values, individual
removal, a batch-wide apply window, review and staged states, and an expandable
live sample. Eight edits cover six supported areas, with four edits seeded.
Stage captures a snapshot; visitors simulate the chosen restart, idle stretch
or timestamp, and only the remaining staged items publish. Player joins reset
the simulated idle wait. The completion receipt exposes the exact before/after
result. Reset cancels any in-progress demonstration. There is no real scheduler,
server restart or automatic interception of
edits elsewhere on the homepage. The installed panel supplies its existing
batch summaries, kinds and actions to the same inventory; demo-specific
before/after values and review actions are optional presentation inputs.

The builder prerenders the real components into declarative shadow roots,
which isolate the panel's tokens and utilities from the marketing CSS. It
scopes canonical token root selectors to `:host` in a hashed stylesheet, so
font, control-size and motion roles also apply inside the shadow roots. It
hydrates the server example immediately and other examples near the viewport.
Without JavaScript, the real UI stays visible and disabled. The installed
panel keeps its original network, loading and authorization wrappers.

For a fast homepage-only preview (without rebuilding the pinned docs):

```sh
cd web/carbon-panel
bun install --frozen-lockfile
bun run build:homepage
cd ../..
python3 -m http.server 18766 --bind 127.0.0.1 --directory .website-build/landing
```

Documentation links require the combined website preview. Generated bundles
and the UI revision/fixture manifest stay under `.website-build/`; commit the
sources, not those outputs. Keep component changes in the website CI path
filters. The marketing site self-hosts IBM Plex; the fragments retain the
panel's current Inter and JetBrains Mono font roles. Font licences are included
alongside the vendored files. See [artwork provenance](homepage-artwork.md).

The browser-console expression in
`scripts/manual-review/homepage-demo-check.js` exercises the built, hydrated
islands through their actual controls, including filtered bulk selection,
download contents, each apply window and reset during pending work. Run it
against a local preview, then check desktop/mobile layout, keyboard controls,
reduced motion and forced colors. Decorative state events only illuminate the
homepage artwork; each fixture retains its independent data and text feedback.

## Social previews

Every published page declares the full Open Graph and Twitter set: type, site
name, title, description, URL, a versioned absolute 1200 by 630 PNG and its alt
text. The homepage, the documentation home and any page without a dedicated
card share `landing/assets/og.png`.

The documentation home, introduction, Docker Compose, API reference and the
design system have dedicated cards in `landing/assets/og-*.png`. Regenerate
them with `python3 scripts/generate_social_cards.py`; the script renders
`assets/branding/social-preview.html` with the website's approved terrain,
logo and vendored IBM Plex fonts. It needs a Chromium-family browser, or use
`--html-only --html-dir .website-build/social-cards` to prepare standalone HTML
for browser captures. Advance each card's `?v=` query when its artwork changes.
The same template renders a 1280 by 640 repository card at
`assets/branding/social-preview.png`. Upload that PNG in GitHub's repository
Settings → Social preview; committing it alone does not change that setting.
`scripts/check_website.py` fails when a page is missing metadata, points at a
relative or missing image, or lets a prominent route fall back to the shared
card. Keep preview titles, descriptions and alt text free of em dashes.

## Advance the pin

1. Select and verify the intended tag/classification in `docs/release-history.json`.
   Keep the peeled commit reachable. Run `version_bump.py bump <tag> --check`;
   excluded or unclassified tags are refused.
2. Review authored docs, imported examples and API changes against that exact
   commit. Update the source docs first, commit them, then pin to the resulting
   commit.
3. Run the atomic `prepare --check`, build and the packaged + browser checks.
   Verify each version banner, switcher, source link, install snippet, download
   behaviour, search scope, API reference, canonical/sitemap URLs, missing-page
   fallback and a link back to the homepage. A v-prefixed source-only version
   must not offer a download CTA.
4. Merge the reviewed change. The one combined Pages artifact deploys only via
   the separately gated dispatch; validation builds never replace the homepage.

Neither publishing a docs pin nor publishing the website creates an application
release. Pinned documentation must not claim live runtime acceptance that has
not been performed.

## Channel promotion gate (OSS-413)

A Pages deployment is a docs channel promotion, so it is gated beyond the
build-only validation. `landing.yml` validates the BUILT site's public
`version-index.json` with `scripts/release.py validate-channel-contract`: the
contract must be `schema_version` 3 with exactly `Stable` and `Nightly` channels
(no version terminology), full 40-hex commits, verified sha256 digests whose
revision equals the commit, stable `latest`+`stable` aliases pinned to the
verified stable digest, nightly with no version tag, and full-SHA
`${repository}/commit/<sha>` pinned links. The removed legacy DOC snapshots
`1.0.39` and `3.0.0-alpha.1` must not appear in the built selector; their source
tags and historical records stay in `docs/release-history.json`.

The same gate requires the trusted `refs/heads/main` source pin, a successful
exact-commit main CI result, and that the built contract pins that SAME commit.
Stale docs therefore cannot be deployed to mask a channel candidate. Both
checks run before the Pages artifact is uploaded and the deploy job additionally
requires their outputs, so a failed gate never reaches the `pages-deploy`
environment-protected job.

A site-only `deploy=true` dispatch is not a new promotion: it reconstructs the
already-active channel source from the live registries and public marker and
passes the qualified-transaction gate with that exact receipt source. All
channel and docs moves share ONE non-cancelling `pages-deploy` lock with no
nested group or self-dispatch. The Nightly revision lives in the published
artifact, marker and receipt — never in a tracked main file updated per build.
See ADR 0052 and [release operations](releases.md).
