REFERENCE / FOUNDATIONS WORKING SYSTEM

The details
that make it Carbon.

The design language shared by Carbon Panel and Carbon Cloud. Explore the colours, typography and controls that turn a collection of features into one considered interface.

A working reference for nineteen Svelte components and their foundations. Examples below are static HTML specimens; the component source remains the implementation.

THEME RESOLUTION

Dark is the default. The dark block is written as :where(:root), .dark, [data-carbon-theme='dark']; :where() contributes zero specificity, so an explicit [data-carbon-theme='light'] container always wins regardless of source order. A plain :root selector would tie with the light rule and win by order, which is why it is not used.

All corners are square. app.css also forces border-radius: 0 !important on every element, so a rounded utility cannot leak in.

FOCUSoutline: 2px solid var(--ring)

.focus-ring applies outline-offset: 2px on :focus-visible only. This page uses a 3 px offset for legibility against documentation borders.

BORDERS1px solid var(--border)

Structural by default. Fields gain a 2 px bottom border on focus or error; the selected tab indicator is a 2 px bar.

DENSITYdata-carbon-density

The stored compact-density preference rewrites these tokens. Layouts must remain usable in both densities; do not hard-code 40 px.

TARGET SIZE24 × 24 CSS px

Minimum pointer target, subject to the WCAG spacing exceptions. Aim for 44 × 44 on touch-heavy actions; a 32 px control must still meet the minimum.

ICON SIZE16 / 20 / 24 px

Inline icons are 16 px and inherit the text colour; standalone icons are 24 px. An icon-only control supplies an accessible name, and no icon carries state alone.

A 32 px control still needs a 24 × 24 CSS px target and adequate spacing. Prefer the 40 px default; reach for sm only in dense, pointer-driven surfaces such as table toolbars.

04 / FOUNDATIONS

Elevation

Three levels. Borders describe structure; shadows separate a floating layer from the page.

LEVEL 00Flat--carbon-shadow-none

Default surfaces, tables, tiles and dense layouts. Separation comes from a 1 px border and a surface change.

LEVEL 01Raised--carbon-shadow-raised

Transient menus, popovers, floating panels and the motion demo object.

LEVEL 02Overlay--carbon-shadow-overlay

Modal dialogs. Always combined with a backdrop and a focus trap, never with a static inline panel.

Motion never carries the only state cue. Animate opacity and transform; avoid transitioning layout properties. An entrance must be interruptible and must never delay an action. Spinners and skeletons stop under reduced motion.

07 / COMPOSITION

Composition rules

How the pieces are assembled. These are the rules that cause the most repeated defects when a route bypasses them.

01

One gutter

CarbonShell owns the main padding, maximum width and vertical rhythm. A route starts with CarbonPageHeader; it does not add p-6, max-w-* or another scroll container.

02

Scroll containers

Every vertical scroll container reserves its gutter (scrollbar-gutter: stable), applied globally to overflow-y-auto, overflow-y-scroll and overflow-auto. This prevents the reflow flicker when content grows past the viewport.

03

Horizontal strips

Tabs and other horizontal strips use scroll-strip: they scroll sideways and paint no bar, so the strip height cannot change. Never add a wrapper with overflow-x-auto that also grows a bar.

04

Nested surfaces

A tile inside a card is a bordered plane, not a shadow. space-y-6 separates page sections; space-y-2 or space-y-4 separates fields and rows. Do not mix a page gutter with a card padding of the same intent.

05

Overlays

Anything fixed goes through a portal to document.body. Rendering inside main places the layer below the fixed header and inside the scroll clip. Dialogs also lock body scroll and restore focus.

06

Widths

Content is capped at max-w-7xl (80 rem). Tables scroll inside their own region. There must be no page-level horizontal overflow at 360, 768 or 1440 px.

DENSITYdata-carbon-density

Compact mode rewrites control and spacing tokens. A layout that hard-codes heights will break. Test both densities and both themes.

RESPONSIVE BREAKPOINTSsm 640 · md 768 · lg 1024 · xl 1280

Tailwind defaults. The shell's side navigation collapses at md; page headers stack below sm.

TAB ORDERDOM order

No positive tabindex. Roving tabindex is limited to composite widgets such as the tab strip.

08 / EXPERIENCE

Interaction patterns

State handling that is not expressible as a component prop.

01

Represent real state

Separate initial loading, empty, filtered-empty, stale, partial and failed. A missing metric is unavailable, not zero. Never render a placeholder value that could be mistaken for data.

02

Name the consequence

Destructive, long-running, billable and permission-sensitive actions state the resource and the outcome before the request. The confirm label repeats the verb, not "OK".

03

Preserve the work

Keep entered values on a recoverable error. Move focus to an error summary for long forms. A failed request must not clear a table or a draft.

04

Keep geometry stable

Reserve the accent-border space, the scrollbar gutter and the loading slot. Hover, selection, focus and menus must not move the layout or target a different row than the one under the pointer.

05

Report honestly

Distinguish submitted, pending, running, complete, failed and unknown. Show progress only when it is measured. Do not imply completion before the backend confirms it.

06

Keep console output intact

Monospace for logs, meaningful line breaks preserved, connection and reconnect state visible. Polling updates must not move the scroll position of someone reading older output.

09 / EXPERIENCE

Accessibility contract

Review dimensions for every component and route. These are targets, not a certification of either application.

4.5:1normal text contrast target

3:1large text and essential non-text boundary target

24 × 24minimum target size in CSS pixels, subject to WCAG exceptions

KEYBOARD

Every action is reachable and operable without a pointer. Composite widgets implement their APG pattern: tabs move selection with arrows, Home and End; dialogs trap and restore focus; disclosure content is removed from tab order when closed.

NAMES AND LABELS

Every control has an accessible name, including icon-only buttons. Visible labels are associated with their field. Hints and errors are referenced with aria-describedby, and invalid state is exposed with aria-invalid.

FOCUS

A 2 px --ring outline at 2 px offset on :focus-visible. Focus styling is never removed without an equivalent. Focus is never moved by polling or by a background refresh.

LIVE REGIONS

Async state changes that the user did not initiate are announced once through a status or alert region. Repeated polling results are not announced. CarbonInlineLoading needs a caller-provided region; CarbonErrorState is already role="alert".

MOTION AND ZOOM

Both reduced-motion paths are supported: the media query and the stored data-carbon-motion attribute. Layouts survive 200% browser zoom and text enlargement, and no content or action is lost at 320 px.

COLOUR AND MEDIA

Meaning is never carried by colour alone. Charts include labels or patterns and a text alternative. Forced-colours mode, translation, RTL and long labels are review dimensions, not assumed to work.

Automated checks catch a minority of these. Test real components in context with a keyboard and a screen reader, including error, loading and reduced-motion states.

10 / WORKFLOW

Change and propagation

The token file is a shared contract. A change is not finished when Panel renders correctly.

  1. Propose the change against the contract.

    Update tokens.css or the component source, and describe the intended effect on both themes, every state, responsive behaviour and compatibility. Do not silently change the meaning of an existing token.

  2. Update Panel, this page and the regression checks.

    The static examples here mirror the Svelte props; a new component or prop must appear on this page in the same change. Run the frontend checks and the design-system tests.

  3. Propagate the snapshot to Cloud.

    Cloud consumes a content-pinned copy with a recorded digest. Its lock records the digest, so ordinary builds need no Panel checkout or network access; a local digest check detects edits to the snapshot. A newer upstream version is only visible through an explicit comparison.

  4. Verify the affected surfaces in both products.

    Keyboard, error, loading, reduced-motion, light and dark themes, both densities, and narrow widths. Tokens do not propagate through hard-coded colours and do not prove behavioural equivalence.

SOURCE OF RECORD

The contract and the propagation procedure are documented in the design-system README. The token values on this page are copied from the canonical stylesheet at build time, not maintained by hand.
