# Release models for Carbon Panel

## What established projects do

- **Home Assistant.** Container users choose `stable` or its `latest` alias, `beta`, or `dev`. Each version also has its own tag. The project runs a beta week before its monthly release, cherry-picks fixes into the beta branch, and publishes release notes and updated documentation with Stable. This gives testers a predictable window and requires a separate preview channel and documentation site. [Versions and channels](https://contributors.home-assistant.io/releases/reference/versions/), [How releases work](https://contributors.home-assistant.io/releases/how-it-works/)
- **Kubernetes and GitLab.** Kubernetes maintains three minor release branches for about a year each and publishes regular patches plus urgent releases when needed. GitLab generally backports ordinary fixes to the current Stable and security fixes to the current and previous two monthly releases, with documented exceptions. Both make maintenance coverage an explicit decision. Each supported line adds backport, qualification and publication work. [Kubernetes supported versions](https://kubernetes.io/releases/version-skew-policy/), [GitLab release and maintenance policy](https://docs.gitlab.com/policy/maintenance/)
- **Version and content identity.** SemVer requires a declared public API and fixes the contents of a published version. Prerelease identifiers sort below the corresponding final version. OCI tags are pointers and multiple tags can refer to a single manifest digest. SLSA build provenance describes how a builder produced an artifact and binds the attestation to the artifact subject. Qualification and approval need separate evidence that names the same artifact. [SemVer 2.0.0](https://semver.org/), [OCI Distribution Specification](https://github.com/opencontainers/distribution-spec/blob/main/spec.md), [SLSA Build Provenance](https://slsa.dev/spec/v1.2/build-provenance)
- **Enforcement differs by surface.** GitHub immutable releases lock the published Git tag and attached assets while allowing edits to release notes and release status. GitHub recommends attaching assets to a draft before publishing. Docker Hub can lock matching tags with a regex so version tags can be protected while channel aliases remain movable. GHCR supports OCI images and digest pulls. Protect the publishing credentials and verify existing tag identities in the workflow wherever registry enforcement is unavailable. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [Docker Hub immutable tags](https://docs.docker.com/docker-hub/repos/manage/hub-images/immutable-tags/), [GHCR documentation](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)

## Recommended fit for Carbon Panel

1. **Offer two channels.** Stable is the default, with `latest` and `stable` pointing to the same qualified digest wherever those aliases are offered. Nightly is opt-in and follows qualified `main` builds independently of Stable. Show the last successful Nightly build and its date so users can tell when it is stale. Keep release candidates optional and separately pinnable as immutable `-rc.N` prereleases. Coordinate any migration of existing aliases with users. [Current Carbon Panel release operations](../releases.md), [Home Assistant channel precedent](https://contributors.home-assistant.io/releases/reference/versions/)
2. **Budget support separately from release timing.** Start with one maintained Stable line and keep older versions available as historical or rollback artifacts. Develop on `main`. An urgent backport to a divergent maintenance branch needs its own trusted qualification path because the current publisher verifies exact main CI and ancestry. Consider a longer support window when maintainers can own its end date, backports and upgrade matrix. Use a release preparation cadence to plan work and allow urgent patches through the same publication gate. [Kubernetes patch releases](https://kubernetes.io/releases/patch-releases/), [GitLab maintenance policy](https://docs.gitlab.com/policy/maintenance/)
3. **Qualify the bytes once.** Save the source commit, OCI index and platform digests, download checksums and qualification receipt. Exercise supported installs and representative existing database, configuration and world data with the pinned candidate. Verify upgrade and rollback on disposable copies and inspect the rendered Stable and Nightly links. Publish the qualified downloads to GitHub and copy the same full multi-platform OCI index by digest into Docker Hub and GHCR. A change to embedded version metadata creates new bytes. If an RC embeds its suffix, qualify a final-version candidate before Stable promotion. [Carbon Panel release operations](../releases.md), [OCI content digests](https://github.com/opencontainers/image-spec/blob/main/descriptor.md#digests)
4. **Make partial publication recoverable.** Serialize registry, GitHub and docs publication. Verify immutable version tags in both registries and attach all GitHub draft assets before exposing moving aliases or Stable-facing links. Record previous and target pointers, verify each public surface after the move, and report completion only after they agree. Resume a partial run from its recorded digests or restore the previous pointers where supported. Refuse an occupied version with different content and issue a new version for a correction. Keep binary rollback guidance tied to the data restore procedure when an upgrade changes persistent state. [GitHub draft and immutable release guidance](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases), [Carbon Panel upgrade and recovery guidance](../releases.md)

## Apply now and evaluate next

- Keep the existing shared GitHub Actions publication lock. Set `queue: max` on every workflow or job that enters it so a second waiting request can keep its place. Arrivals at the lock determine queue order, and the queue has a finite limit. Continue validating live source and artifact identity under the lock before each write. [GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
- Consider enforcing immutability for full version tags in each provider after rehearsing retries, recovery and historical tag handling. Provider settings affect outside writers and deserve their own qualification. Keep moving aliases outside such a restriction. [Docker Hub immutable tags](https://docs.docker.com/docker-hub/repos/manage/hub-images/immutable-tags/), [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)
- Keep tracking separate channel identities and preserve the last verified docs and image pair for each. The site currently carries both channels in one deployment, so a Stable update needs proof of the Nightly identity it preserves. Evaluate whether a future publisher can preserve that receipt during a Nightly outage while reporting Nightly's degraded state accurately. Keep the existing parity gates in place until that path has real recovery evidence. [Carbon Panel channel promotion](../adr/0052-channel-promotion-gates.md)
